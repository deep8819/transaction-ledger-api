# Transaction Ledger API

## 1. Overview

This is a small web API for keeping a ledger. You create accounts, record credits and debits against them, check a balance, and read the transaction history. Every transaction is saved together with its balance change, so the history and the balance always agree. Transactions cannot be edited or deleted through the API.

Tech stack: Python, FastAPI, SQLite, SQLAlchemy, Pydantic.

## 2. Setup and run (Windows PowerShell)

Run all commands from the project folder (the one that contains `requirements.txt`).

First-time setup:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Start again later:

```powershell
.\.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload
```

Run the tests (with the virtual environment active):

```powershell
python -m pytest -v
```

The test suite has 33 tests.

Interactive API pages (served by the running app, default port):

- Try the endpoints: `http://127.0.0.1:8000/docs`
- Health check: `http://127.0.0.1:8000/health`

The database is a file called `ledger.db`. It is created automatically at start-up. The path in the code is relative (`./ledger.db`), so the file is created in the folder you start the server from. Start the server from the project folder every time, or you will get a second, empty database.

Stop the server with Ctrl+C. A running server keeps `ledger.db` open, so stop it before deleting that file.

```
    error.py                    Error reply shape (used in /docs)
  models/                     Database tables (SQLAlchemy)

    types.py                    Money column type (Decimal in Python, whole hundredths in the database)
  services/                   Business rules
    account_service.py          Create account, read balance
    transaction_service.py      Create transaction, list history

  conftest.py                 Test setup: temporary database and a small test client

```

A request flows: route, then schema (checks the input), then service (business rules), then model (database), and back out through the reply schema.

## 4. API reference

There are five endpoints: the four ledger endpoints below, plus `GET /health`.

All money values are returned as strings with two decimals (for example `"100.00"`). All ids are UUID strings generated by the server. The examples below are real requests and responses captured from a running server (ids and times will differ on your machine).

### GET /health

Response `200`:

```json
{"status": "ok"}
```

### POST /accounts

Creates an account. The client sends only `name`.

| Field | Type | Rules |
|---|---|---|
| `name` | string | Required. Surrounding spaces are removed. Must not be empty after that. |

Any other field (for example `balance`) is rejected with `422`.

Request:

```
POST /accounts
{"name": "  Alice  "}
```

Response `201`:

```json
{
  "id": "aa89e219-26e5-49c2-8b7b-86609f78be70",
  "name": "Alice",
  "balance": "0.00",
  "created_at": "2026-10-27T12:04:10.741537"
}
```

### GET /accounts/{account_id}/balance

Returns the current balance. Unknown account: `404 ACCOUNT_NOT_FOUND`.

Request:

```
GET /accounts/aa89e219-26e5-49c2-8b7b-86609f78be70/balance
```

Response `200`:

```json
{
  "account_id": "aa89e219-26e5-49c2-8b7b-86609f78be70",
  "balance": "82.00"
}
```

### POST /accounts/{account_id}/transactions

Records a credit (adds to the balance) or a debit (subtracts from it).

| Field | Type | Rules |
|---|---|---|
| `type` | string | Required. `"credit"` or `"debit"`. |
| `amount` | number or numeric string | Required. Greater than 0. At most 2 decimal places. Maximum `9999999999.99`. |
| `description` | string | Optional. Surrounding spaces are removed. |
| `reference_id` | string | Required. Surrounding spaces are removed. Must not be empty after that. Must be unique within the account. |

Any other field is rejected with `422`.

Request:

```
POST /accounts/aa89e219-26e5-49c2-8b7b-86609f78be70/transactions
{"type": "credit", "amount": 100, "description": "  salary ", "reference_id": "ref-1"}
```

Response `201`:

```json
{
  "id": "250dd9fc-0af6-47da-9da4-1ebd1bd43db5",
  "account_id": "aa89e219-26e5-49c2-8b7b-86609f78be70",
  "type": "credit",
  "amount": "100.00",
  "description": "salary",
  "reference_id": "ref-1",
  "created_at": "2026-10-27T12:04:10.849023"
}
```

Possible errors: `404 ACCOUNT_NOT_FOUND`, `409 INSUFFICIENT_FUNDS`, `409 DUPLICATE_TRANSACTION`, `422 VALIDATION_ERROR`.

### GET /accounts/{account_id}/transactions

Returns the account's history, newest first.

| Query parameter | Default | Rules |
|---|---|---|
| `type` | none (both) | `credit` or `debit` |
| `page` | `1` | Whole number, minimum 1 |
| `limit` | `10` | Whole number, 1 to 100 |

Reply fields: `transactions` (the list), `page`, `page_size`, `total_records`, `total_pages`. The totals follow the `type` filter.

Request:

```
GET /accounts/aa89e219-26e5-49c2-8b7b-86609f78be70/transactions?type=credit&page=2&limit=2
```

Response `200`:

```json
{
  "transactions": [
    {
      "id": "0d28157c-10fe-401b-a68b-3ec2825a121f",
      "account_id": "aa89e219-26e5-49c2-8b7b-86609f78be70",
      "type": "credit",
      "amount": "10.00",
      "description": null,
      "reference_id": "ref-3",
      "created_at": "2026-10-27T12:04:10.908095"
    },
    {
      "id": "250dd9fc-0af6-47da-9da4-1ebd1bd43db5",
      "account_id": "aa89e219-26e5-49c2-8b7b-86609f78be70",
      "type": "credit",
      "amount": "100.00",
      "description": "salary",
      "reference_id": "ref-1",
      "created_at": "2026-10-27T12:04:10.849023"
    }
  ],
  "page": 2,
  "page_size": 2,
  "total_records": 4,
  "total_pages": 2
}
```

A page past the last page returns `200` with an empty `transactions` list and the correct totals (real run: `page=99` gave `"transactions": []`, `"total_records": 5`, `"total_pages": 1`).

Possible errors: `404 ACCOUNT_NOT_FOUND`, `422 VALIDATION_ERROR`.

## 5. Error format

Every error uses this shape:

```json
{"error": {"code": "ACCOUNT_NOT_FOUND", "message": "Account not found", "details": []}}
```

`details` is empty except for validation errors. For those, each item has `field` and `message`:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [
      {"field": "body.type", "message": "Input should be 'credit' or 'debit'"},
      {"field": "body.amount", "message": "Input should be greater than 0"},
      {"field": "body.reference_id", "message": "String should have at least 1 character"}
    ]
  }
}
```

`field` is `body.<name>` or `query.<name>`. For a request body that is not valid JSON, `field` is just `body`.

| Code | HTTP status | When it happens |
|---|---|---|
| `ACCOUNT_NOT_FOUND` | 404 | The account id does not exist. Any id that is not an existing account gives this, including text that is not a UUID. |
| `INSUFFICIENT_FUNDS` | 409 | A debit is larger than the current balance. |
| `DUPLICATE_TRANSACTION` | 409 | The account already has a transaction with this `reference_id`. |
| `VALIDATION_ERROR` | 422 | Wrong or missing field, extra field, bad `type`, bad `amount`, bad `page`/`limit`, or malformed JSON. |
| `INTERNAL_ERROR` | 500 | Any unexpected error. The message is always generic. The real error is written to the server log only. |
| `NOT_FOUND` | 404 | The URL does not exist. |
| `METHOD_NOT_ALLOWED` | 405 | The URL exists but not for that HTTP method. |
| `HTTP_ERROR` | varies | Any other web-level error. It exists in the code but I did not trigger it. |

## 6. Design decisions

**Money is stored as whole hundredths, handled as Decimal.** Python code uses `Decimal`, never `float`. SQLite has no exact decimal type, so the `Money` column type in `app/models/types.py` saves each amount as a whole number of hundredths (the smallest unit, such as cents or paise) and converts back on reading. It refuses more than 2 decimal places. The request rule is `TransactionCreate.amount` in `app/schemas/transaction.py`. The app has no currency field, so the currency is up to you.

**Creating a transaction is atomic.** `create_transaction` in `app/services/transaction_service.py` changes the balance and adds the transaction row, then calls `commit()` once. That is the only commit in the function. Any error, including the 404, duplicate and insufficient-funds checks, runs `rollback()` first. The result is either both changes saved or neither. An automated test (`tests/test_atomicity.py`) forces a crash just before the commit and checks that nothing was saved.

**Duplicates are blocked twice.** First, `create_transaction` looks for an existing transaction with the same account and `reference_id` and stops with `DUPLICATE_TRANSACTION`. Second, the table has a database rule, `UniqueConstraint("account_id", "reference_id")` (named `uq_transaction_account_reference`) in `app/models/transaction.py`. If that rule fires, the service rolls back and returns the same error. The rule is per account, so another account can reuse the same `reference_id`.

**Transactions are immutable through the API.** `app/routes/transactions.py` has only a POST and a GET route for transactions. There is no update or delete route. A `DELETE` on the transactions URL returns `405`. The database itself does not block edits, so this protection is at the API level only.

**History is sorted newest first with a stable tie-break.** `list_transactions` orders by `created_at` descending, then `id` descending. The tie-break keeps the order the same between requests when two transactions share a timestamp. Filtering, counting, sorting and slicing are all done in the database query.

**`total_pages` rounds up.** It is `(total_records + limit - 1) // limit` in `list_transactions`. With 5 records and a limit of 2, that is 3 pages. Rounding down would leave the last record unreachable. With 0 records, it is 0 pages.

## Database constraints

Built from the real schema (`sqlite_master` in `ledger.db`). "Enforced by the database" means a direct SQL statement that skips the app is refused.

| Table | Rule | Enforced by the database? | Notes |
|---|---|---|---|
| `accounts` | Primary key on `id` | Yes | Unique and never NULL. |
| `accounts` | `NOT NULL` on `id`, `name`, `balance`, `created_at` | Yes | |
| `accounts` | `UNIQUE`, `CHECK`, `FOREIGN KEY` | No | None are declared on this table. |
| `transactions` | Primary key on `id` | Yes | Unique and never NULL. |
| `transactions` | `NOT NULL` on `id`, `account_id`, `type`, `amount`, `reference_id`, `created_at` | Yes | `description` is optional on purpose. |
| `transactions` | `UNIQUE` `uq_transaction_account_reference` on (`account_id`, `reference_id`) | Yes | Per account. Another account may reuse the same `reference_id`. |
| `transactions` | `CHECK` `ck_transaction_type`: `type IN ('credit', 'debit')` | Yes | Case-sensitive. `'CREDIT'` is refused. |
| `transactions` | `CHECK` `ck_transaction_amount_positive`: `amount > 0` | Yes | |
| `transactions` | `FOREIGN KEY` `account_id` to `accounts(id)` | Yes | Enforced only on connections that turn foreign keys on, which the app does in `app/database.py`. Another tool that opens `ledger.db` does not enforce it unless it turns the setting on itself. |

- "A balance can never go negative" is enforced by `create_transaction` in the service, not by the database. The `accounts` table has no `CHECK` on `balance`.
- Immutability of transactions (no edit or delete) is enforced at the API level only.

## 7. Assumptions

Each item below was checked against the code and, where noted, a real run.

- **Extra request fields are rejected with 422.** Confirmed in a real run for `balance` on `POST /accounts` and for an unknown field on `POST .../transactions`.
- **Account names are trimmed and not unique.** Confirmed: `"  Alice  "` was saved as `"Alice"`, and a second `"Alice"` account was created.
- **Ids are UUIDs.** Account and transaction ids are generated by the server. An unknown id, or text that is not a UUID (tested with `not-a-uuid`), returns 404.
- **`description` is optional.** Left out, it comes back as `null`. A description of only spaces is trimmed to an empty string and returned as `""`, not `null` (real run).
- **Insufficient funds and duplicate `reference_id` both return 409.** They have different codes: `INSUFFICIENT_FUNDS` and `DUPLICATE_TRANSACTION`.
- **The same `reference_id` on a different account is allowed.** Confirmed in a real run. The uniqueness is on the pair (account, `reference_id`) and does not depend on the transaction type (from code).
- **A rejected transaction is not saved, so its `reference_id` can be reused.** Confirmed: a debit with `ref-3` was rejected for insufficient funds, and a later credit with `ref-3` was accepted.
- **Amounts: at most 2 decimal places, and the maximum is `9999999999.99`.** The code allows 12 digits in total with 2 after the decimal point, which leaves 10 digits before it. A real run accepted `9999999999.99` and rejected `10000000000`, `10000000000.00` and `999999999999` with "no more than 10 digits before the decimal point". Also rejected: `0.001` (too many decimals), `0` and `-5`. Accepted: `100.1` (stored as `100.10`), the string `"100.10"`, and `1e2` (stored as `100.00`).
- **A balance has no maximum of its own.** Only each single amount is capped. A real run took one account's balance to `10000000300.29`, above the per-amount cap.
- **A debit equal to the balance is allowed.** Only a debit larger than the balance is rejected (from code, `data.amount > account.balance`; not run).
- **Pagination.** `page` starts at 1, `limit` defaults to 10 with a maximum of 100, and a page past the last returns an empty list. `page=0`, `limit=0`, `limit=101` and `page=abc` return 422 (real run for `limit=101`, tests for the others).
- **`reference_id` is case-sensitive and trimmed.** In a real run `ref-1` and `REF-1` on the same account were both accepted as different references. `"  ref-1  "` was treated as `ref-1` and rejected as a duplicate. A `reference_id` of only spaces gives 422. The value is stored and returned in the trimmed form, with the original capitalisation.
- **`created_at` has no timezone marker in the output.** The real output looks like `2026-10-27T12:04:10.741537`, with no `Z` and no offset. The value is in UTC: the code writes UTC, and during the run the stored time matched UTC and not the local time of the machine (which is 5 hours 30 minutes ahead). The marker is lost because SQLite stores plain text without a timezone. Clients should treat `created_at` as UTC.
- **SQLite is a local file.** For production, use a server database (for example PostgreSQL) and add migrations. See section 10.

## 8. Concurrency

Two debits arriving at the same moment on one account are handled in `create_transaction`.

How it works on SQLite:

1. The first thing the function does is run a harmless `UPDATE` on the account row (it sets `balance` to its own value). The first write starts the database transaction and takes SQLite's write lock. This lock covers the whole database file, not just one row.
2. Any other request that tries to write must wait. The balance is only read after the lock is held, so a second debit sees the balance left by the first one.
3. The lock is released at `commit()` or `rollback()`.

What I confirmed by running it:

- The no-op `UPDATE` takes the write lock, even when no row matches. While it was open, a second connection could not start a write ("database is locked"), but could still read.
- Ten simultaneous debits of 60 against a balance of 100 were sent five times. Each time, exactly one succeeded (`201`), nine got `409`, and the final balance was `40.00`.
- Ten simultaneous identical credits (same `reference_id`) were sent five times. Each time, exactly one succeeded, nine got `409`, and the balance was `10.00`.

Limits:

- **Only one writer at a time.** The lock is for the whole database file.
- **Waiting has a time limit.** SQLite waits up to 5 seconds (`busy_timeout` was 5000 ms). In a real run, a writer that waited longer got `500 INTERNAL_ERROR` after about 6 seconds. No data was written. The code does not turn this into a friendlier error.
- **The test was small.** 10 parallel requests from one computer, to one server process. I did not test heavy load or several server processes.
- **This technique is specific to SQLite.** On PostgreSQL, a no-op `UPDATE` would lock only that account's row. I did not run it there. The safer standard approach is to lock the row explicitly (`SELECT ... FOR UPDATE`) or to do one conditional update ("subtract only if the balance is large enough").
- **The duplicate fallback is SQLite-specific.** When the database's unique rule fires, the code recognises it by looking for the text `UNIQUE constraint failed` in the error. PostgreSQL words this error differently, so that check would need changing, or a race would return `500` instead of `409` (from reading the code).

## 9. Bonus: transfer (not implemented, design only)

A transfer would move money from one account to another. This is how I would build it:

- It is one endpoint that takes a source account, a destination account, an amount and a `reference_id`.
- Everything happens inside one database transaction, with one commit at the end.
- First, check that both accounts exist. If either is missing, stop with "account not found". Reject a transfer where the source and destination are the same account.
- Lock both accounts, always in the same order (for example, the account with the lower id first). If two opposite transfers (A to B and B to A) run at once and each locked its own source first, they could wait for each other forever. A fixed order prevents that.
- With the locks held, read the source balance and check it covers the amount. If not, stop with "insufficient funds".
- Then take the amount from the source and add it to the destination, and write one debit record and one credit record, all in the same transaction.
- If anything fails at any step, roll back everything. Neither balance changes and no record is saved.
- For `reference_id`: use the one the client sends on both records. The uniqueness rule is per account, so the same value on two different accounts is allowed. If the client retries the same transfer, the source account already has that `reference_id`, so the retry is refused as a duplicate and nothing moves twice.
- The two records would also need to be linked, so the history can show they belong to one transfer. The current table has no column for that, so one would need to be added.

## 10. Known limitations and future work

- **No migrations.** Tables are created only if missing. Changing an existing table (for example adding the unique rule) does not update an old `ledger.db`; the file had to be deleted and recreated during development.
- **SQLite only.** One database file, one writer at a time. See sections 7 and 8 for moving to a server database.
- **Foreign keys are enforced only on connections made by the app.** `app/database.py` runs `PRAGMA foreign_keys=ON` on every new SQLite connection it opens, so the database rejects a transaction for a missing account. SQLite sets this per connection, so another tool that opens `ledger.db` (for example a database viewer) does not enforce it unless it turns the setting on itself.
- **`created_at` has no timezone marker.** See section 7.
- **A long lock wait returns a generic 500.** See section 8.
- **No endpoints to list accounts or fetch one account's details.** Only the balance can be read.
- **No login or permissions.** Anyone who can reach the server can use every endpoint.
- **A whitespace-only `description` is stored as an empty string** instead of `null`.
- **No cap on a balance.** A very large balance could exceed SQLite's integer range. I did not test this (see "Could not verify").
- **History sorting has no supporting index.** Only `account_id` is indexed. This could slow down very large histories.
- **The database file path depends on where the server is started.**
- **Add `CHECK (balance >= 0)` on `accounts` so the database itself refuses an overdraft, and block `UPDATE`/`DELETE` on `transactions` with a trigger or permissions.** Today both rules are enforced only by the app (see "Database constraints").
- **The list of tests does not include a test for concurrency.** The concurrency results in section 8 came from manual runs.

- **Minimum Python version.** I only ran Python 3.14.7. The code uses `str | None` type hints, which need Python 3.10 or newer, but I did not test any other version.
- **Minimum package versions.** `requirements.txt` says `>=`, but I only ran these versions: fastapi 0.162.0, starlette 1.10.0, uvicorn 0.54.0, SQLAlchemy 2.1.6, pydantic 2.14.1, pytest 9.1.1.
- **First-time setup from nothing.** I did not recreate `.venv` from scratch in this session. The `venv` and `pip install` steps are the standard ones, and an existing `.venv` was used for all runs.
- **PowerShell script permissions.** I did not test whether `Activate.ps1` is blocked by your PowerShell execution policy on a fresh machine.
- **Anything on PostgreSQL.** The statements about PostgreSQL in sections 8 and 10 come from reading the code and general knowledge, not from running it.
- **A balance beyond SQLite's integer range.** I expect a database error and a `500`, with the change rolled back, but I did not run it.
- **Several server processes or heavy load.** Concurrency was tested with 10 parallel requests to one server process only.
- **The `HTTP_ERROR` code.** It is in `app/errors.py`, but I did not trigger it.
- **Server logging.** The code writes the real error to the log on a `500`. A test checks that the log text appears and the client body leaks nothing, but I did not read the log output of the live server.
- **Every `curl` or PowerShell variant of the requests.** The example requests were sent with a Python script, not typed into PowerShell. They show the exact method, path and JSON body. The `/docs` page is the easiest way to try them.
